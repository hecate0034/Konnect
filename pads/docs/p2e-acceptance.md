# P2 第五批：原生逻辑连接核验

日期：2026-11-06 至 2026-11-07；版本：0.6.0；分支：`codex/pads-native`。

## 本批范围

新增只读 MCP 工具 `inspect_pads_logical_connectivity`（领域工具总数 21）。
它沿用测试副本、会话身份和工程/数据库/库路径约束，不运行器件打包或 PCB 同步。
输入为设计名称及 1–16 组明确的位号/物理脚号，可指定同范围基线进行比较。

每次调用在全新证据目录运行安装内固定的 `SctNetlist.exe` 与 `AllegroNetlist.exe`，
读取绑定工程的 `DxD` 快照、`DX` 流程；校验两种格式的引脚归属一致，再重复整轮
导出与选定实时引脚读取。拒绝诊断输出、缺失/截断结果、冲突或不支持语法、状态变化。
两个格式使用同一 Siemens 数据库引擎，不能视为两个独立电气求解器。

实时核对包含完整实例路径、局部器件/引脚/网络 UID、页面和导出网络成员关系。
不会因为局部名称或 UID 相同就合并网络；SCT 的 `E-NETS` 分组也不用于合并 `NETS`。
导出名称仅在该设计/报告内标识网络，不冒充持久 UID。失败不登记为成功基线。

## 真实测试用例

使用官方 `PADS_Professional_Eval` 完整示例的新副本：
`.pads-runtime/p2e/fixture/LessonFinal/LessonFinal.prj`。

- 全局 GND：根页 C2.2 与层次实例 U27.8；全局 VDD：C10.1 与 U27.16。
- 层次端口：U9.64、U13.AD8、U27.13 都归属 `U9LO1`。
- 重复层次隔离：U27.15 与 U29.15 的局部器件 UID、引脚 UID、页面、网络 UID/名称
  均相同；完整实例路径分别在 `IO_Port1`、`IO_Port2` 下，导出网络分别为
  `$1N3_IO_Port1`、`$1N3_IO_Port2`，结果必须保持不连通。
- 缺失引脚、共用单元脚 U6.8、实例脚号为空的 U12.4，以及不同选定脚集合的基线均拒绝。
- 临时复用放置 C900 后，原生导出报 `Design is not packaged!`。工具返回
  `logical_design_unpacked`，即使有部分导出文件也不采信；恢复 C900 后重新核验。
- 既有 U25.6 原本悬空。在 FPGA2 页预览三段正交路径，再接入 GND 的已有拐点。
  核验只有 GND 的成员集合改变，器件声明不变；关闭重开后核验，再显式恢复并重开，
  最终全导出图和选定脚记录应与原始基线一致，两个操作页的记录也应还原。

## 验收结果

**30 个实际 MCP 请求通过，耗时 661.91 秒。** 成功记录目录：
`.pads-runtime/p2e/evidence/p2e-4bf2e6d0`；汇总：
`.pads-runtime/p2e/evidence/p2e-acceptance-designer.json`。

原始导出为 119 个封装器件、320 个逻辑网络、1,233 个已连接导出引脚；
其中 10 个选定引脚完成实时路径/身份核对。U25.6 接线后仅 GND 成员增加该引脚，
器件声明不变；第一次重开后结果一致。恢复及第二次重开后，全导出图、选定脚记录和
两个操作页的已记录状态全部与初始基线一致。不能将 1,233 个导出引脚数当作
1,233 个已独立核对实时映射的引脚。

原始 1,613 个文件与副本中库/PCB/Verify.ini 共 1,263 个受保护文件 SHA-256 未变。
收尾核对所属 GUID、PID、启动时间、工程路径及原始网格值 254000 后，通知本次宿主
正常退出；确认编辑器退出后再次核对相同文件指纹，结果一致。
记录在 `.pads-runtime/p2e/evidence/p2e-cleanup.json`。正式工程和 GLK 库未写入。

回归：**145 项 Python、13 项 Rust 测试通过**；Rust 构建、格式与 Clippy 严格检查通过，
六个本批 Python 文件的 Black 检查通过。原有参考/只读 MCP 冒烟检查通过 11 个响应。
能力查询确认选定逻辑连接验收标记为 true，通用写入验收仍为 false。

新增测试覆盖两种格式一致性、截断/歧义/重复赋网、共用电源脚声明、层次局部 UID
隔离、E-NETS 不合并物理成员、未打包/零退出码诊断、全新导出路径、选定脚范围、
错误基线与失败不入库，以及两轮读取间图、实时引脚、库、导出程序和数据库路径变化。

## 发现的问题与明确限制

1. 新增器件涉及打包状态。只读工具不会自行打包、分配脚号或重编号。打包有潜在跨页、
   库映射及位号影响，应另建预览/影响范围和恢复流程，不能为使导出通过而偷偷执行。
2. U12 的实时实例脚号为空，虽然原生导出能通过库映射获得脚号，本批仍拒绝该选择。
   U6/U7 的共用电源脚在 SCT 中有重复声明；只去重一致声明并保留重复元数据，
   不据此声称多单元实时映射已验证。隐藏脚、总线直接连接和全部库脚映射尚未覆盖。
3. 全图导出用于成员差异比较；实时物理映射只核对请求中的引脚。
   `full_design_pin_mapping_verified` 和 `full_erc_verified` 保持 false。
4. 仅验证本机 VX.2.4 / COM 66。严格语法与数量上限可能拒绝其他工程，应扩展有证据
   的格式支持，不静默截断。原生导出每个 25 秒，原生工作进程 180 秒，上层 270 秒。
5. 其他界面操作不能被此工具锁定；重复观察稳定不等于数据库原子快照。原有恢复机制
   也不是原子事务。专有示例、手册、原始导出和完整类型库证据只留本机。

开发探查中还发现 `RinfNetlist.exe` 对示例长网名报错但退出码为零，因此未选作
受支持导出器。前两轮验收分别暴露 U12 隐式脚号和新器件未打包；第一轮无写入，
第二轮记录了 C900 的显式恢复，随后干净导出通过。失败证据保留，未冒充通过记录。
